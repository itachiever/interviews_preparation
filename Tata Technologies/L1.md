## Question 5: Suppose we already have a centrally maintained reusable security workflow. Can you write a caller workflow that triggers whenever a pull request is raised against the `main` branch and securely passes scanner credentials (secret key and secret ID)?

Answer:

Yes. I would create a caller workflow that listens for pull requests targeting the `main` branch and invokes the centrally maintained reusable security workflow.

I would use the `pull_request` event with the `branches` filter to restrict execution to pull requests targeting `main`.

Inside the `jobs` section, I would use the `uses` keyword to reference the existing reusable workflow.

For scanner credentials, I would explicitly map the required secrets using the `secrets` block instead of using `secrets: inherit`. This ensures that only the required credentials are passed to the reusable workflow.

I would also configure the minimum required workflow permissions and ensure that credentials are stored in GitHub Secrets rather than hardcoded in the workflow.

## Question 6: How would you define the workflow name, configure the pull request trigger, specify the required branch, configure permissions, invoke an existing reusable workflow, and pass secrets securely?

Answer:

I would structure the caller workflow like this:

```
name: Security Scan

on:
  pull_request:
    branches:
      - main

permissions:
  contents: read
  security-events: write

jobs:
  security:
    uses: ./.github/workflows/reusable-security.yml
    secrets:
      SCANNER_SECRET_KEY: ${{ secrets.SCANNER_SECRET_KEY }}
      SCANNER_SECRET_ID: ${{ secrets.SCANNER_SECRET_ID }}
```

Here is how it works:

1. Name: `Security Scan` identifies the workflow.
2. Trigger: `pull_request` triggers the workflow when a pull request event occurs.
3. Branch filter: `main` ensures the workflow runs for pull requests targeting the main branch.
4. Permissions: I configure only the permissions required by the workflow. For example, `contents: read` allows repository checkout, while `security-events: write` is needed if the workflow uploads code-scanning results to GitHub.
5. Reusable workflow: The `uses` keyword invokes the existing reusable workflow from its YAML file path.
6. Secrets: The `secrets` block explicitly maps the scanner secret key and secret ID from GitHub Secrets.

The reusable workflow must also define these inputs under `on: workflow_call` and declare the corresponding secrets.

This approach promotes reusability, centralizes security logic, and avoids exposing unnecessary credentials to individual workflows.

## Question 8: Suppose a security scanner returns JSON data containing scan status and vulnerability findings. Can you write a Python function that checks the JSON data and raises an error if it finds any high- or critical-severity vulnerabilities?

Answer:

Yes. I would load the scanner's JSON response, extract the findings, iterate through them, and check the severity of each finding.

If any finding has a `High` or `Critical` severity, I would raise an exception so that the pipeline can fail and prevent the application from progressing.

For example:

```
import jsondef security_check(json_data):    data = json.loads(json_data)    findings = data.get("findings", [])    for finding in findings:        severity = finding.get("severity", "").lower()        if severity in ["high", "critical"]:            raise Exception(                f"Security scan failed: {severity} vulnerability found"            )    print("Security scan passed")
```

Here, `json.loads()` converts the JSON string into a Python dictionary.

Then, `data.get("findings", [])` extracts the findings. I iterate through each finding and check its severity.

The `in` operator checks whether the severity matches either `high` or `critical`.

If a matching vulnerability is found, the exception stops normal execution. When this function is executed in a CI/CD pipeline, the failure can be used to enforce the security quality gate.

## Question 10: Suppose a developer accidentally commits production credentials (secret keys and IDs) directly into the main branch, and those credentials also make it into the production environment. As a DevSecOps engineer, how would you contain the damage and prevent other team members from accessing the exposed credentials?

Answer:

I would treat this as a security incident and focus first on reducing the blast radius, then removing the exposed credentials and preventing recurrence.

My approach would be:

1. Revoke and rotate credentials: Immediately revoke the exposed production credentials and generate new credentials. I would update the affected applications and services with the new credentials through a secure secrets-management solution.
2. Assess the impact: Identify where the exposed credentials were used, check access logs for suspicious activity, and determine whether there was any unauthorized access.
3. Restrict access: Ensure the old credentials are no longer valid and verify that access to the replacement credentials is restricted through appropriate IAM roles and permissions.
4. Remove credentials from Git history: Identify the commit containing the exposed credentials and rewrite the repository history to remove the sensitive information. Coordinate this with the development team because history rewriting requires team members to synchronize their local branches.
5. Enable secret scanning: Enforce secret scanning in the CI/CD pipeline so that hardcoded credentials are detected before code is merged.
6. Developer awareness: Guide developers on using environment variables and secret-management services instead of storing credentials directly in source code.

In our environment, I would also make secret scanning a mandatory security quality gate and ensure that any detected secrets are reported and handled immediately.

The most important point is that simply deleting the credentials from the latest commit is not sufficient. We must revoke the credentials and remove the exposed values from the repository history as well.

## Question 11: After rotating or revoking the compromised credentials, how would you remove the exposed credentials from Git history so that team members cannot retrieve them when pulling the main branch?

Answer:

After revoking the compromised credentials, I would remove them from the entire Git history rather than simply deleting them from the latest version of the file.

My approach would be:

1. Identify the commit and all files containing the exposed credentials.
2. Use a history-rewriting tool such as `git filter-repo` to remove the sensitive values from all affected commits.
3. Force-push the rewritten history to the remote repository after coordinating with the repository administrators and development team.
4. Ask team members to discard or clean up their old local branches and re-clone the repository or synchronize with the rewritten history.
5. Verify that the exposed credentials are no longer present in the remote branches and tags.

For example, `git filter-repo` can be used with a replacement file to replace sensitive strings throughout the repository history.

I would also check other locations where the credentials might have been copied, such as forks, pull-request references, build logs, artifacts, and cached pipeline outputs.

One important point is that rewriting Git history does not make an exposed credential safe. Credential revocation and rotation must happen first. History cleanup is an additional measure to prevent further accidental exposure.

## Question 12: If you have implemented secret scanning in your CI/CD workflow, how would you distinguish between test secrets and active production secrets, considering that scanners identify both as secrets?

Answer:

Most secret-scanning tools identify potential secrets based on predefined patterns, entropy, and known credential formats. They can detect that a string looks like a secret, but they generally cannot reliably determine whether that credential is currently active or belongs to a production environment.

In our environment, we considered this a practical challenge.

One approach we followed was implementing additional pattern matching and validation rules based on our organization's requirements.

For example:

- Identify known test or dummy credential patterns, such as values containing `test`, `sample`, or other approved indicators.
- Apply pattern matching based on credential formats and naming conventions.
- Use file-path and repository-context matching where appropriate.
- Maintain approved exceptions for known test credentials, with proper review and ownership.
- Treat unknown or potentially active credentials as security findings requiring investigation.

Where supported and authorized, we can also validate credentials through the relevant provider's API or secret-management platform to determine whether they are active.

However, I would not rely only on naming conventions or pattern matching to classify a credential as inactive. Any exception should be documented, reviewed, and periodically reassessed.

The objective is to reduce false positives without allowing genuine production credentials to bypass security controls.

## Question 13: Suppose an internal pull request workflow cannot access scanner credentials, so the team forks the scanner credentials from another pull request. A team member suggests using `pull_request_target` and checking out the entire contributor branch. Would you accept this solution? Why or why not?

Answer:

No, I would not accept that approach as it introduces a significant security risk.

The `pull_request_target` event runs in the context of the base repository, which means it can have access to repository-level secrets and permissions that are not normally available to an untrusted pull-request workflow.

If we use `pull_request_target` and then check out and execute code from the contributor's branch, we could unintentionally execute untrusted code with access to sensitive credentials.

For example, a malicious contributor could modify a build script, dependency configuration, or workflow-related script to capture and expose scanner credentials.

I would therefore avoid checking out or executing untrusted pull-request code in a privileged workflow.

Instead, I would separate the validation of untrusted code from privileged security operations and use a controlled mechanism to provide the required scanner access.

The key principle is that untrusted pull-request code should never be allowed to execute with privileged credentials.

## Question 14: If you reject the `pull_request_target` approach, what alternative solution would you suggest to securely provide scanner credentials to the workflow?

Answer:

I would suggest separating the pull-request validation workflow from the privileged security-scanning workflow.

My preferred approach would be:

1. Run the initial pull-request validation using the standard `pull_request` event without exposing sensitive credentials.
2. Use a trusted, centrally maintained reusable workflow for security scanning.
3. Keep scanner credentials in GitHub Secrets or an enterprise secrets-management solution.
4. Provide credentials only to the trusted scanning job, using explicit secret mapping and minimum required permissions.
5. Avoid executing untrusted contributor scripts or build steps in a job that has access to privileged credentials.

If the scanner requires authentication, another option is to use a dedicated service account with restricted permissions or short-lived credentials through OIDC, where the scanner and identity provider support it.

For workflows that genuinely need privileged access, I would ensure that the privileged operation is isolated from untrusted code and that the workflow checks out only trusted code.

This approach maintains security while allowing automated scanning to be integrated into the pull-request process.
